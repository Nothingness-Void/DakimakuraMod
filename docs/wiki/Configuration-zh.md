# 配置项参考

_[English version / 英文版本](./Configuration.md)_

Dakimakura Mod（Nothingness-Void 维护分支）提供两个 Forge 配置文件，可通过 **Mods → Dakimakura Mod → Config** 界面内编辑，保存后会热加载。首次启动时自动生成。

| 文件 | 作用范围 | 路径 |
|---|---|---|
| `dakimakuramod-common.toml` | 服务端与单机宿主 | `<gameDir>/config/dakimakuramod-common.toml` |
| `dakimakuramod-client.toml` | 仅客户端 | `<gameDir>/config/dakimakuramod-client.toml` |

联机时以服务端的 common 配置为准，客户端连接后会使用服务端给的参数做图片传输。

磁盘缓存里的纹理以"内容 + 相关参数"的 SHA-256 作 key，**修改下面任何一个服务端参数都会自动让旧缓存失效**，不会渲染出错位缓存产生的脏图。

---

## Common（服务端）选项

位于 `dakimakuramod-common.toml` 的 `[server]` 段。

### `maxTransferHeight`

- **类型**：整数，256 - 8192
- **默认**：`1536`

服务端下发抱枕纹理前的最大高度。宽度按 1 : 3 比例自动换算（高度 1536 对应宽度 512）。

**为什么重要**：爬虫下载的源图常常是 4096 × 12288 甚至更大。原样下发到客户端会占大量带宽与显存，但抱枕本身体积很小，放大到 1536 之上在正常视距下几乎看不出区别。1536 的高度能把一张抱枕的传输量压到原始值的十分之一左右。

**什么时候调**：

- 带宽紧张、玩家抱怨首次进服加载久，降到 `1024` 或 `768`
- 带宽非常充裕且玩家会近距离观察抱枕细节，可以调到 `2048` 或 `3072`

### `jpegQuality`

- **类型**：小数，0.10 - 1.0
- **默认**：`0.80`

对"不透明 + `smooth = true`"的纹理做 JPEG 重编码时使用的质量。透明图不会走 JPEG，这项对它们无效。

**为什么重要**：对照片/插画类图片，JPEG 0.80 通常能把一张图压到原 PNG 15 ~ 30% 的大小，肉眼基本看不出差别。

**什么时候调**：

- 还想更激进压缩又不想明显掉画质：`0.70`
- 复杂画面要进一步省带宽：`0.60`（会比 0.80 柔一点，但传输量再砍一半）
- 图细节极其重要，宁愿多占带宽：`0.90 - 1.0`（基本等于关 JPEG 压缩）

### `maxSourceMegabytes`

- **类型**：整数，1 - 1024
- **默认**：`32`

单张源图文件大小硬上限，超过即跳过（对应抱枕会显示为缺失纹理）。

**为什么重要**：作为一个安全阀。没有它，一张 500MB 的异常 PNG 在任何尺寸检查之前就会被完整读进内存。这个限制在调用 `ImageIO` 打开文件之前生效。

**什么时候调**：

- 只有确实需要导入超大 PNG、且服务端内存充裕时再上调
- 绝大多数情况下不需要降低

### `memoryCacheMinutes`

- **类型**：整数，1 - 1440
- **默认**：`10`

服务端内存缓存中，一份优化后的纹理在最后一次访问后保留多长时间。超时的条目会自动淘汰。

**为什么重要**：内存缓存是最快的路径。五个玩家在这段时间内都请求同一张抱枕，只有第一个会真正跑图像处理流程，剩下四个直接从 RAM 拿数据。

**什么时候调**：

- 并发玩家多、世界中抱枕数量多、且堆内存充裕：调到 30 ~ 60
- 服务端内存紧张或者并发很低：降到 3 ~ 5

### `diskCacheEnabled`

- **类型**：布尔
- **默认**：`true`

服务端是否把每张优化后的纹理同时持久化到磁盘。

**为什么重要**：磁盘缓存打开后，每个（图片 + 参数）组合的图像处理流程**只跑一次**。服务端重启、新玩家加入、内存缓存到期，之后都直接从磁盘取现成的字节。

**什么时候调**：

- 除非是不希望在磁盘上落下任何状态（只读文件系统、极小 SSD 等），否则一直开着就好

### `diskCacheMegabytes`

- **类型**：整数，0 - 65536
- **默认**：`1024`

服务端磁盘缓存的总大小软上限。超出后按最近访问时间最旧的先淘汰。设为 `0` 完全不限制。

**为什么重要**：单张优化后的纹理通常就几百 KB，1GB 能放下大量抱枕。这个上限主要是防止有人丢几千个包之后目录失控增长。

**什么时候调**：

- 小 VPS 磁盘紧张：适当降低
- 专用服务器磁盘够大：调高或设为 `0`

## 客户端选项

位于 `dakimakuramod-client.toml` 的 `[client]` 段。

### `memoryCacheMinutes`

- **类型**：整数，1 - 1440
- **默认**：`20`

客户端显存中的抱枕纹理在最后一次访问后保留多长时间。超时后会从显存释放，下次看到再重新上传。

**为什么重要**：GPU 纹理上传代价不低，把它们留在显存里可以避免"回头再看一次就卡顿一下"这种体验。单张抱枕占用的显存大约是 `maxTransferHeight × (maxTransferHeight / 3) × 2 × 4` 字节（前后两面 + RGBA）。

**什么时候调**：

- 显存小或装了很多其它吃显存的 mod：降到 5 ~ 10
- 显存充裕，很在意来回走动时的微卡顿：调到 60 以上

### `diskCacheMegabytes`

- **类型**：整数，0 - 65536
- **默认**：`2048`

客户端磁盘缓存总大小软上限，存放在 `<gameDir>/dakimakura-mod-cache/`。`0` 表示不限制。

**为什么重要**：客户端磁盘缓存是"掉线重连快"的关键。本地已经有这张抱枕的纹理字节（按 hash 索引）时，服务端就不用再发。对网络不稳定、或者服务端有大量自定义抱枕的场景，这是最大的体验改善。

**什么时候调**：

- 默认 2GB 能放下几千张纹理，对大多数人够用
- SSD 空间小、且你常在纹理频繁变动的服务器之间切换：适当降低
- 常在多个重度自定义的服务器之间切换，希望全都本地保留：调高或设为 `0`

## 缓存目录一览

| 路径 | 所属 | 作用 |
|---|---|---|
| `<gameDir>/dakimakura-mod/` | 服务端 | 源 `daki-info.json` 和图片文件，即 pack 目录 |
| `<gameDir>/dakimakura-mod-server-cache/` | 服务端 | 优化后的、随时可发的纹理字节，按 hash 索引 |
| `<gameDir>/dakimakura-mod-cache/` | 客户端 | 客户端收到的纹理本地副本，也按 hash 索引 |

这三个目录任何时候都可以安全删除。pack 目录会在下次启动时自动把内置的 Vanilla Mobs 重新释放进去；两个缓存目录会按需重新填充。

## 纹理哈希如何保证缓存不脏

每张抱枕纹理的 SHA-256 指纹包含：

- 哈希版本标记
- 该抱枕 `daki-info.json` 里的 `smooth` 开关
- 服务端参数 `maxTransferHeight`、`maxSourceMegabytes`、`jpegQuality`
- 正面图路径与字节
- 背面图路径与字节

由此保证：

- **改任何一个配置都会自动让旧缓存失效**，不会渲染出"在别的参数下优化出来的错图"
- **替换一张图只会让那个抱枕的缓存失效**，其它抱枕仍然命中
- **两个抱枕恰好共用同一张图时会在缓存层去重**，只占一份存储与传输带宽

因此修改配置或更新包时不需要手动清缓存。旧条目会被自动忽略，之后由 LRU 软上限淘汰。
